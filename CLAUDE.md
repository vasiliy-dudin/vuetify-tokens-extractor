# Architecture & design rationale

This document exists to hand off context to another engineer or AI agent picking up this tool. It explains *why* things are built this way, not just what the code does — read `README.md` first for usage, this file for the reasoning behind the implementation.

## Problem this solves

Vuetify component styling (padding, radius, colours, states, sizes) needed to be fed into a Figma Agent to audit/align a design system and generate Figma Variables. The obvious approaches were rejected for cost/fidelity reasons:

- **Rendering every variant/size/state combination in a browser and screenshotting/inspecting computed styles** — correct but expensive (dev server, browser automation, one pass per combination).
- **Reading raw SASS source defaults** (`_variables.scss`) — cheap, but wrong whenever a consumer project overrides SASS variables via `@use 'vuetify/settings' with (...)` or applies a blueprint (md1/md2/md3). Vuetify's own `packages/api-generator` already does this for docs API tables, and it was considered and rejected for this reason.
- **This tool's approach**: parse the *compiled* CSS output (which already reflects any SASS overrides baked into that build) plus generate the runtime theme headlessly in Node. This is both cheap (no browser) and correct under customisation.

## Two independent data sources, deliberately kept separate

Vuetify styling comes from two places that never overlap, and the tool mirrors that split internally:

1. **Compiled CSS** (`dist/vuetify.css` or a consumer's own build) — everything driven by SASS: padding, radius, layout, per-variant/size/density modifier classes. SASS variable overrides are only observable here, because they're baked in at compile time. `src/parser.mjs` owns this.
2. **Runtime theme** (`--v-theme-*`, `--v-hover-opacity`, etc.) — generated by Vuetify's JS (`composables/theme.ts`) and injected as a `<style>` tag at runtime. **Not present in the compiled CSS at all** — grep for `--v-theme-primary:` in `dist/vuetify.css` and you'll find only consumers (`var(...)`), never a definition. Blueprints (md1/md2/md3) affect *only* this side — they set JS theme colours and component prop defaults, never SASS. `src/theme.mjs` owns this, and it was confirmed experimentally that `createVuetify(...).theme.styles.value` and `.theme.computedThemes.value` compute correctly in plain Node with no DOM/browser (the SSR code path in Vuetify already does this — `getOrCreateStyleElement` guards only the DOM-write, not the string computation).

`src/serialize.mjs` / `src/condense.mjs` recombine both: every CSS declaration keeps its raw `var(--v-...)` reference, and a resolved value is substituted in *if* theme data was generated. Resolution is opt-out (`--no-theme`), never silently skipped.

## Component enumeration

Component names and their CSS class base (`VBtn` → `v-btn`) come from `<vuetify>/dist/json/importMap.json` (+ `importMap-labs.json` for labs components), which Vuetify's own build already emits — no need to hand-maintain a component list. One override exists: `VApp → v-application` (`components.mjs::CLASS_BASE_OVERRIDES`), the one component whose root class isn't a literal kebab-case of its name.

## CSS rule classification (`src/parser.mjs`)

This is the trickiest part of the tool and the source of every non-obvious bug found so far.

### Exact class-token matching, not substring matching

A class token belongs to component `v-btn` iff it **is** `v-btn`, or **starts with** `v-btn--` / `v-btn__`. Naive substring matching would wrongly pull in `v-btn-group` and `v-btn-toggle` (different components that happen to share a text prefix). Tokens inside `:not(...)` are treated as conditions, never as ownership.

### Compound-selector anatomy

Every selector is split into space/combinator-separated *compounds* (`.v-pagination .v-btn:hover` → `['.v-pagination', '.v-btn:hover']`). The last compound that owns a token of the target component is the **subject**; everything before it is **context** (potential ancestor).

For the subject compound, three *different* kinds of "foreign class" must not be conflated — this distinction was gotten wrong once and had to be fixed:

| Location | Example | Meaning | Field |
|---|---|---|---|
| A compound **before** the subject, itself belonging to another registered component | `.v-btn-group--divided .v-btn` | Real ancestry — this rule only applies inside that container | `conditions.contextComponent` |
| A foreign class in the **same compound** as the subject | `.v-checkbox.v-input` | Composition, not ancestry — VCheckbox reuses VInput's base class on the *same element* | `conditions.combinedWith` |
| A foreign class in a compound **after** the subject | `.v-btn .v-icon` | A descendant this component styles | `conditions.childComponent` |

Only `contextComponent` routes an entry to the `contextual` bucket (and gets excluded from the compact output as "not this component's own styling" — the styles apply only inside another component). Early versions of this tool merged the same-compound case into `contextComponent` too, which silently deleted a component's own base styles whenever it composed another component's class (`VCheckbox`, `VRadio`, every input-family component). If you're debugging "component X has no output," check whether its rules are same-compound-combined with another component's class before assuming the CSS truly doesn't exist.

### Bucket routing priority

`forcedColors` / `mediaQueries` / `supports` (at-rule wrapped) → `contextual` (ancestor match) → `variants` → `sizes` → `densities` → `states` (boolean modifiers or interaction pseudo-classes) → `elements` (`__foo`) → `modifiers` (any other `--foo`) → `base`. First match wins; nothing is discarded — every entry keeps its full `selector` and a `conditions` object recording every modifier/pseudo/attribute/element/context it had, even if only one of them decided the routing.

## Two output formats

### Compact (default)

Flat map keyed by space-joined condition parts (`"variant:elevated state:hover"` → `{prop: value}`). Built for **token budget**, specifically because the first full-fidelity version produced ~90 KB JSON per component and the Figma Agent consuming it couldn't handle files that large. Two lossy trade-offs were made deliberately:

1. **Property allowlist** (`condense.mjs::DESIGN_PROP_RE`) — drops layout/interaction plumbing (`display`, `position`, `transition-property`, ...) that a designer can't express in Figma anyway, keeping colour/typography/spacing/sizing/effects properties. This is a hand-maintained regex and the most likely place to lose data silently if a new CSS property class needs to be considered "design-relevant" — it already had one bug (matched `width$`/`height$` exactly, missing `min-width`/`max-width`/`min-height`/`max-height`, which broke every component's declared `min-width`). **If a token is unexpectedly missing from compact output, check this regex before assuming a parser bug.**
2. **Cascade collapse per key** — later declarations for the same `(bucket-key, prop)` simply overwrite earlier ones (last-wins, mirroring CSS cascade order), rather than preserving every historical override.

### Full (`--full`)

One entry per matched CSS rule, structured by bucket, nothing dropped or merged — the `condense.mjs` allowlist and collapsing don't apply. Use this to debug the parser itself, or when downstream tooling can handle the extra size.

Both formats share the same `extractComponent()` output from `parser.mjs`; only the serialisation differs (`serialize.mjs` for full, `condense.mjs` for compact).

## The defaults fallback is loud on purpose

Theme input is never inferred. With no `--vuetify-options` / `--blueprint` / `--theme-css`, `loadOptions` returns `{}` and `generateTheme` reports `source: 'defaults'`, so every resolved colour is Vuetify's built-in palette (`primary: #1867C0`). That output is plausible and wrong, and it shipped silently once: a consumer changed `primary` in their app, rebuilt, ran the tool, and got the old colour back — the app's `createVuetify()` config was never read, and never could be, because theme colours aren't in the compiled CSS at all (see above).

`cli.mjs` therefore warns on stderr whenever `themeData.source === DEFAULT_THEME_SOURCE`, naming the `primary` actually used, and records the same one-line note as `$meta.themeWarning`. The warning is printed *after* the per-component warning loop so it survives the `--all` flood.

**That field must never be renamed to `warning`.** `meta` is spread into every component's `$meta` (`condense.mjs`, `serialize.mjs`), and `cli.mjs` uses `json.$meta.warning` as the "this component matched no CSS rules, skip writing it" signal. A key called `warning` inside `meta` would make that test true for *every* component, writing zero files and reporting no error.

## Package boundary and path resolution

This started as a script embedded in the Vuetify monorepo (`scripts/style-tokens/`), with paths hard-coded relative to that repo (`../../packages/vuetify`). It was extracted into this standalone package so it can be version-pinned and reused across projects without manual copy-pasting on every update (consumed as a git dependency pinned to a tag, e.g. `"vuetify-tokens-extractor": "github:<you>/vuetify-tokens-extractor#v0.2.0"`).

Extracting it required removing every monorepo-specific assumption:

- **`src/vuetify-root.mjs`** resolves the installed `vuetify` package via `require.resolve('vuetify/package.json', { paths: [cwd] })` instead of a relative path. This transparently supports both a normal npm/pnpm install *and* a pnpm-workspace symlink (confirmed by running this tool from inside the Vuetify monorepo root, where `vuetify` resolves to the workspace-linked `packages/vuetify`). `--vuetify-root <path>` is the escape hatch for anything resolution can't find.
- **`postcss`** became a direct `dependencies` entry of this package rather than being resolved out of Vuetify's own `node_modules` (the original script reused Vuetify's devDependency, which doesn't exist once this tool lives elsewhere).
- **jiti** is a direct `dependencies` entry for the same reason as `postcss`, and is imported lazily (only when `--vuetify-options` points at a `.ts`/`.mts`/`.cts` file) so `.mjs` consumers don't pay for it. It has no transitive dependencies. It exists because a consumer's theme config usually lives in TypeScript next to the app source, and Node's own TS support is both version-dependent (`engines` here allows 18.17) and limited to erasable syntax.
- **No bundled theme preset.** The original in-monorepo script defaulted to a hard-coded copy of the Vuetify docs app's theme config (blueprint md3 + custom colours) — reasonable when the tool had one consumer, wrong for a generic package: a "docs" preset means nothing outside that one repo. It was therefore deleted, **not relocated** — an earlier version of this document claimed it "now lives in the Vuetify repo as `scripts/vuetify-tokens.config.mjs`", which was never true and directly caused the silent-defaults bug described below. This tool has zero project-specific knowledge; theming input is always explicit (`--blueprint`, `--vuetify-options`, `--theme-css`, or nothing = Vuetify's own defaults), and the consumer owns its own `vuetify-tokens.config.{mjs,ts}`.
- **Options files must be plain data.** `--vuetify-options` is imported in plain Node (or jiti), so it cannot be the app's own Vuetify plugin file: that imports `vuetify/styles` and `vuetify/components/*` (CSS, no loader in Node), often pulls in packages that do the same, may rely on bundler auto-imports (`h`, `camelize`), and commonly exports an install function rather than the options object. The supported shape is a side-effect-free module exporting the theme as data; see README for the `theme.ts` + `vuetify-tokens.config.ts` pair.

## Known limitations / things a future change might need to revisit

- `DESIGN_PROP_RE` is a hand-picked allowlist, not derived from anything — any CSS property family not anticipated there silently disappears from compact output. When output looks incomplete, check this first.
- `combinedWith` / `childComponent` only track a *single* foreign component reference (`??=` first-match). A rule referencing two different foreign components in one selector would only record the first.
- Related/multi-block components (e.g. `VDataTable` → `v-data-table-column`, `v-data-table-header`, ...) are detected heuristically by string prefix in `parser.mjs::findRelatedBases` and nested under `relatedBlocks`, not treated as first-class components — deep enough for the current use case, but not exhaustive.
- Runtime theme mutation after `createVuetify()` is invisible here. The Vuetify docs app is a live example: `@vuetify/one`'s settings store overwrites `theme.themes.value` with its own `blackguard`/`polaris`/`nebula`/`odyssey`, and its `blackguard` differs from the one the app declares. `light`/`dark` are untouched and `light` is the default, so ordinary output is faithful — but any `blackguard` output does not match the running site.
- Alias-keyed `defaults` (e.g. a `PrimaryBtn` alias of `VBtn`) never reach `propDefaults`: `componentDefaults()` keys on the real component name. Sharing an app's `aliases` block with the tool is also impossible, since it requires importing real components, which import CSS.
- `mediaQueries` / `forcedColors` / `supports` buckets exist in the full format but are entirely excluded from compact output (design tools can't express conditional media queries), so anything only defined behind those at-rules is invisible in the default format.
- The `~59` "no CSS rules matched" warnings on `--all` (as of the last check) are mostly legitimate — renderless components, transition wrapper components, icon components with no unique class — but this list hasn't been individually audited component-by-component; a warning is a prompt to check, not proof of a bug.
